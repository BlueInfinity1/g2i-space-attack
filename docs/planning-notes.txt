Components:
- GameController: start/playing/game-over state, score, start and restart orchestration.
- ScoreCalculator (proposed after prompt 009): pure calculation of a kill award from enemy type/base score, pre-death formation/attacking state and vertical depth. GameController applies the award once to the session total.
- PlayerController: keyboard movement, playfield bounds and fire input.
- ShipHealth: current/max health, damage, brief player invulnerability, damage/death events. Player health is configurable. Every enemy is fixed at 1 health with no damage invulnerability, so one valid player projectile hit destroys it.
- Weapon: firing cadence, projectile spawning and team ownership; shared by player/enemy.
- Projectile: travel, lifetime, 2D trigger hits, team filtering and single-hit consumption.
- EnemyController: formation/attacking states, constant-speed diagonal-only attack movement and defeat notification; weapon use only if enemy firing is included after reference clarification.
- WaveDirector: complete formation setup at stage start, selection of existing enemies to attack, stage completion and bounded difficulty scaling.
- HUDView: score, health, wave, controls, start screen, game-over screen and restart button.
- FeedbackController: impact flashes, explosions, audio and restrained camera shake.
- Config ScriptableObjects: PlayerConfig, EnemyConfig, WeaponConfig, WaveConfig, FeedbackConfig and the proposed ScoringConfig; a thin GameConfig root references these assets for setup.

The config categories are implemented under Assets/SpaceAttack/Scripts/Data and Assets/SpaceAttack/Settings. docs/game-config-proposal.txt preserves design rationale; the C# classes and config assets are the implementation source of truth.

Enemy types and scoring proposal after prompt 009: use three EnemyConfig assets sharing one EnemyController. Proposed formation-kill values from the user's observations are red 30, green 40 and yellow 60. Moving enemies use a shared 4x-to-10x multiplier increasing with vertical depth, rounded to tens; the level number does not affect score. Award only on a player-projectile kill, once, using state/position captured before death cleanup. See docs/scoring-proposal.txt. This approximates the described behavior; the exact original moving-score formula has not been measured. This supersedes the original single-type/flat-score proposal.

One-hit enemy rule clarified in prompt 010: red, green and yellow enemies all die from one valid player projectile hit, whether in formation or attacking, at every level. Remove configurable enemy baseHealth from the current scope; use fixed 1-health enemies and player projectile damage 1. The previous reference to nonlethal hits was generic wording, not a proposed tougher enemy type. Award-once logic prevents duplicate awards from repeated collision/death callbacks. Player health and invulnerability remain separate mechanics.

Flow: input -> player/weapon -> projectile -> ship health -> death/damage events -> score/waves/UI/feedback. Explicit Inspector references and small events; no dependency injection framework or global service locator.
GameController owns session state and score. ShipHealth owns health. WaveDirector owns wave progression. Restart clears spawned entities and resets session, health, weapons and waves; subscriptions must not accumulate.
